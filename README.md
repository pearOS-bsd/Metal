# Metal

Metal.framework for pearOS BSD: the Metal API (`MTLDevice`, `MTLCommandQueue`, buffers, textures, render / compute / blit encoders, events, libraries) implemented over Vulkan, with the same Objective-C ABI as Apple's `Metal.framework` (install name `/System/Library/Frameworks/Metal.framework/Versions/A/Metal`).

**Layer 2 (core frameworks).** Why: Apple's `RenderBox` (SwiftUI's renderer), CoreImage, QuartzCore's glass effects and every Metal application draw through it. See the `SwiftUI` repository.

Status: planned, nothing implemented yet.

## Plan
1. Surface first: `docs/API-SURFACE.md` lists every `MTL*` symbol and protocol selector that real RenderBox, SwiftUICore, QuartzCore and CoreImage import (read with REA from the cache, never committed), ordered by use.
2. `MTLCreateSystemDefaultDevice` + queue + buffer + texture + render pass over Vulkan (Mesa lavapipe in the VM, virgl / real GPU later); `IOSurface`-backed textures.
3. Shaders: Apple's `.metallib` is AIR (LLVM bitcode). A translator AIR to SPIR-V of our own (LLVM's SPIR-V backend is Apache-2.0 and may be used; `steelbrain/metal2vulkan` is GPL/LGPL and stays a measuring tool only, nothing copied). Test bed: the 180 functions of QuartzCore's `default.metallib` (see `Solarium/docs/METAL-SHADERS.md`: 18/18 glass shaders already translate).
4. Compare against the real Metal on the Mac (differential tests, same pattern as QuartzCore).
5. MetalKit, MetalPerformanceShaders later.

## Findings of 2026-11-20 (first contact with the real Metal.framework on pearOS)
Evidence and the run that led here: `SwiftUI/docs/EVIDENCE.md`.
* The real SwiftUI app (Calculator) on the real dyld + cache reaches Metal and stops there: `-[MTLIOAccelServiceGlobalContext init]: IOServiceAddMatchingNotification failed e00002c7` (kIOReturnUnsupported), repeated by several threads; no window. The generic part of Apple's Metal looks for `IOAccelerator` services in IOKit and loads the GPU driver plug-in they name; there is no such service, so there is no `MTLDevice`.
* Consequence for the design: faking the IOKit accelerator for the real Metal would mean reimplementing the kernel's IOAccelerator user-client ABI and a closed driver's command stream. The plan stays: **our own Metal.framework** (an `MTLDevice` implementation over Vulkan) that takes the place of Apple's in the process. Open problem: how it takes the place of the copy in the dyld cache, which RenderBox and QuartzCore are already bound to.
  * `DYLD_INSERT_LIBRARIES`: the real dyld then stops using the shared cache for the program (Foundation "slice is not valid mach-o"): not usable.
  * A normal extra dependency (`tools/trace-device/add-dylib.py` adds an `LC_LOAD_DYLIB`) is loaded fine (an empty C library: Calculator runs as before). `__DATA,__interpose` tuples for `MTLCreateSystemDefaultDevice`, `MTLCopyAllDevices` and `IOServiceAddMatchingNotification` were **never called** (no log) although the failing init runs: either the calls are not made through the exported symbols, or interposing does not reach those cache images in this dyld setup. To find out first: interpose a symbol that is certainly called (`getpid`) from the same kind of library, then read who calls `MTLIOAccelServiceGlobalContext init` (backtrace of the thread, as in `SwiftUI/docs/EVIDENCE.md`).
  * An ObjC library built with `-fobjc-arc` on the Mac VM (`tools/trace-device/mtltrace.m`) as an extra dependency crashes the process in `objc_autoreleasePoolPop` on a workqueue thread (also seen in `lsd-objc`): a darwinator / workqueue problem to look at before ObjC code of ours runs inside a SwiftUI process.
* `tools/trace-device`: `mtltrace.m` (a device object that logs every selector sent to it) and `add-dylib.py`; written, **not yet shown to work**.

## Second pass (2026-11-20, later): how Apple's Metal finds a GPU, and where we plug in
Measured on the real Calculator (SwiftUI app) on pearOS with libraries added as an `LC_LOAD_DYLIB` (`tools/trace-device/add-dylib.py`; `__DATA,__interpose` works for functions called from cache images, tested with `getpid`; earlier "no log" was `fopen` not writing in that process: log with `write(2, ...)`).
* **Who asks:** the real **AppKit** at startup (`NSApplication` setup) calls into Metal; Metal calls `IOServiceMatching("IOAccelerator")`, `IOServiceGetMatchingServices`, `IONotificationPortCreate`, `IOServiceAddMatchingNotification("IOServicePublish")`, `IOServiceOpen`. So every real AppKit app asks for a GPU, not only SwiftUI ones.
* **What Metal does with an accelerator service** (decompiled `_getMetalPluginClassForService` in the 26.7.2 cache): reads the registry property `MetalPluginName` (a string), `gpu_bundle_find_trusted(name, path, 0x400)` finds the driver bundle, `NSBundle`, then the property `MetalPluginClassName` (or the principal class) and checks that the class is a subclass of the expected base; the class makes the `MTLIOAccelDevice`. The generic layer (`MTLIOAccelDevice`, `MTLIOAccelCommandQueue`, resources) sits on `IOAccelerator.framework` (`IOAccelDeviceCreateWithAPIProperty`, `IOAccelCommandQueue*`, `IOAccelResource*`, user client of the kernel driver); the vendor plug-in encodes GPU commands. Apple's own virtual GPU works the same way (a paravirtual driver bundle).
* **So the way that does what Apple does:** (1) an `IOAccelerator` node in darwinator's IOKit registry (`darwinator/src/mach_ipc.c`, table `io_nodes`, properties in `io_property_bin`) with `MetalPluginName` / `MetalPluginClassName`, matching and the publish notification working; (2) our driver bundle (`PearMetalDriver.bundle`, trusted path under `/System/Library/Extensions`) with the class that Apple's Metal instantiates, implementing the device, queue, buffers, textures, encoders over Vulkan through a native FreeBSD helper (a Mach-O process cannot call the ELF Vulkan loader: sockets and shared memory like `wsbridge`). Apple's Metal front end (library loading, validation, `MTLCopyAllDevices`, device observers) then stays Apple's. Unknown until (1) works: which other properties and which `IOAccel*` calls the generic layer makes before it asks the plug-in.
* **Not done:** neither (1) nor (2). `darwinator` prints nothing for these requests at `debug` 1 or 2; the IOKit lines of `io_serve` have to be checked (are the matching calls reaching `io_serve` at all?).

## Third pass (2026-11-20, night): the real Metal instantiates our driver class
What works now on pearOS (real dyld + cache, real Metal / AppKit, `darwinator` with the new IOKit nodes, `tests/mtldevice.m` as the probe):
1. `darwinator/src/mach_ipc.c`: an `IOAccelerator` node `pear-gpu` in `io_nodes` with the properties `MetalPluginName` = `PearMetalDriver`, `MetalPluginClassName` = `PearMTLDevice`; the notification request (id 2884, `IOServicePublish` + `IOProviderClass IOAccelerator`) answers with an iterator over the matching nodes; `io_registry_entry_get_registry_entry_id` (2871) and the interest notification (2869) are answered.
2. `driver/`: `PearMetalDriver.bundle` (`sh driver/build.sh OUT` on a Mac; goes to `/System/Library/Extensions`). Apple's `_getMetalPluginClassForService` finds it (`gpu_bundle_find_trusted` accepted a bundle there; no code signature needed in this setup), loads it, and `MTLCopyAllDevices` -> `_MTLRegisterDevices` -> `-[MTLIOAccelServiceGlobalContext registerService:deviceClass:]` calls `[[PearMTLDevice alloc] initWithAcceleratorPort:14083]`.
3. What Metal asserts of a device (found one by one): the class must be a subclass of `MTLIOAccelDevice` (it sends `_setAcceleratorService:`), conform to `MTLDevice` and to the private `MTLDeviceSPI` (added at run time with `class_addProtocol` from Metal's own protocol object); its `dealloc` must not run Apple's base `dealloc` (it releases queues that never existed: crash), so the bundle is built without ARC. Then `-featureProfile` is asked (returns 10002 for now, the value a Mac with Intel Xe reports).
4. `PEAR_METAL_LIST=1` makes the bundle print every method of `MTLDeviceSPI` (398) as the **work list** of the device; `MTLDevice` itself is the other list (the SDK header).
5.
